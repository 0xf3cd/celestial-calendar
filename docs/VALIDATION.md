# Validation

<a id="validation"></a>
## Numerical Validation

Tests live in `src/test/` and check numerical results against external reference data with per-column
tolerances. Each data set records its source, how it was generated and why its tolerance was chosen, so it can be
rebuilt and audited. `src/test/jieqi_golden_test.cpp` is a complete example; [`AGENTS.md`](../AGENTS.md) gives the
conventions. External references include:

- **JPL Horizons**: apparent positions of the Sun, the Moon and Mercury through Pluto, and Jieqi crossings,
  collected or replayed by `moon_horizons_crawler.py`, `planet_horizons_crawler.py`, `pluto_horizons_crawler.py`,
  `sun_equatorial_horizons_crawler.py` and `sun_jieqi_golden_crawler.py` in `statistics/`.
- **Hong Kong Observatory almanac**: the published Jieqi clock times for 2022–2028. The whole calculation chain
  must agree within 60 seconds, a margin that mostly absorbs the almanac's own rounding to the minute. Implemented
  by `automation/jieqi_table.py`; the entry point is `./checks.py --jieqi-table`.
- **ytliu0's ChineseCalendar**: an independent lunar-year table pinned to a commit, used to validate the
  pre-generated algorithm; see `src/test/lunar/algo3_ytliu0_golden_test.cpp`.
- **ΔT observations**: the NASA eclipse ΔT table, USNO observations, and Stephenson & Morrison. They give UT1 ↔ TT
  conversion a baseline that does not depend on this library's fitted models; see
  `src/test/astro/julian_day_test.cpp`.
- **Sunrise and sunset references**: USNO / NOAA / JPL DE, with a tolerance of ±2 minutes.
- **Swiss Ephemeris 2.10.3bfinal**: formula-level and date-level reference values for the Equal, Whole Sign and
  Placidus house systems, generated by `statistics/house_swiss_crawler.py`.

`statistics/` holds the data-collection scripts and evaluation notebooks. Install their dependencies in a virtual
environment with `python -m pip install -r Requirements-statistics.txt`. The [references](../README.md#references)
keep the original source links.

<a id="replay-margins"></a>
## Chart Snapshot Replay Margins

[`docs/examples/chart_snapshot/data.json`](examples/chart_snapshot/data.json) stores one complete chart snapshot.
The automation tests replay it through the C++ core, the installed Python package through the C ABI, and the
JavaScript package tests through WASM. Each field is held to one of five absolute margins in
[`bindings/python/test/consumer/chart_replay.py`](../bindings/python/test/consumer/chart_replay.py);
`bindings/javascript/test/support/chart_replay.mjs` uses the same values.

These are replay acceptance margins. They bound how far a fresh run may drift from the stored values; they do not
say how close the positions are to the sky. That evidence comes from the external references above.

The values are the thresholds the snapshot test used when the example was added for #300
(`automation/tests/test_chart_snapshot_example.py` in commit `9a7a692`). #331 (`a6efe58`) moved them into
`chart_replay.py` without changing a value. It changed one thing about how they are applied: longitude, the four
axes and the house cusps are now compared around the circle, so values on either side of 0°/360° count as close.

They are separate from the margins in
[`bindings/python/test/consumer/golden_replay.py`](../bindings/python/test/consumer/golden_replay.py). Those were
measured: they are the largest residuals of the release wheels on four platforms (#217), and they apply to
`toolbox/bindings_golden.json`, which holds no chart data.

<a id="base-head"></a>
## Comparing Values Between Two Commits

A change that should not move any number, such as a refactor or an include cleanup, can be checked by running the
same inputs through the old and the new code and comparing every value and every exception. This is evidence for
one change, not a retained check: it is not committed, CI does not rerun it, and it compares the code with its own
earlier version, not with an external reference. If a comparison turns up behavior worth pinning, add a test with
reference data as described under [Numerical Validation](#validation).

Write a probe: a small C++ program that calls the functions the change touches over a fixed sample of inputs and
prints one line per call. Print values with `%.17g`, which tells every binary64 value apart, and catch exceptions
so their type and message are printed too. For example:

```cpp
#include <cstdio>
#include <exception>
#include <typeinfo>

#include "delta_t.hpp"

int main() {
  using astro::delta_t::Model;
  for (const auto model : { Model::ALGO1, Model::ALGO2, Model::ALGO3, Model::ALGO4, Model::ALGO5 }) {
    for (int year = -4100; year <= 3100; year += 25) {
      std::printf("model=%d year=%d ", static_cast<int>(model), year);
      try {
        std::printf("value %.17g\n", astro::delta_t::compute(model, year));
      } catch (const std::exception& e) {
        std::printf("throw %s: %s\n", typeid(e).name(), e.what());
      }
    }
  }
}
```

Keep the probe outside the source tree. From the root of the checkout that holds the change, extract the base
commit to a temporary directory, compile the probe against both trees with one compiler and one set of options,
and compare the outputs:

```sh
(
  set -euo pipefail
  base=main                                     # the commit or branch to compare against
  probe=/path/to/probe.cpp
  compile() { clang++ -std=c++23 -O2 "$@"; }    # the same compiler and options for both sides
  work=$(mktemp -d)
  mkdir "$work/base"
  git archive "$base" | tar -x -C "$work/base"
  compile -I"$work/base/src/astro" -I"$work/base/src/calendar" -I"$work/base/src/util" "$probe" -o "$work/probe-base"
  compile -Isrc/astro -Isrc/calendar -Isrc/util "$probe" -o "$work/probe-head"
  "$work/probe-base" > "$work/base.txt"
  "$work/probe-head" > "$work/head.txt"
  test -s "$work/head.txt"
  diff "$work/base.txt" "$work/head.txt"
  wc -l < "$work/head.txt"
)
```

The commands run in a subshell, so `set -euo pipefail` stops them at the first failed step without closing an
interactive shell. A failed archive or build, a probe that exits non-zero, an empty output and any difference each
stop the run before the row count. The second build uses the working tree, uncommitted edits included.
`git archive` does not touch the checkout, and every output goes to the temporary directory. If a header moved
between the two commits, change the include paths for that side only. A row count as the last line means every
sampled call returned the same value or threw the same exception type with the same message.

The result has two limits, and a report of it should state both:

- Sample: it holds only for the inputs the probe sampled. Name them and give the row count.
- Toolchain: it holds only for that compiler, standard library, set of options and platform. Another toolchain can
  round the last bits differently. Name the compiler, its version and the options.

A pull request that cites such a comparison should also name the base commit.

## Jieqi JSON Table Export

An application that only needs Jieqi order and spacing, and does not want to link the library, can use
`toolbox/jieqi_table.py` to export `query_jieqi_moment` as a static JSON table (#164). Build the shared library
first as described in [Building from Source](BUILDING.md#build), then run from the source root:

```sh
python3 toolbox/jieqi_table.py
python3 toolbox/jieqi_table.py -o build/jieqi.json --start-year 2000 --end-year 2031
```

The first command writes the default 1950–2051 table to standard output, 24 × 102 = 2448 entries. The second
chooses an output file and a year window; the years must lie within `[401, 9999]`. The output contract:

- Each entry is `{year, idx, name_zh, unix_ms, iso_utc}`. `idx` counts from Lichun (立春) = 0 and follows the ABI's
  `to_index` order; `name_zh` comes from the ABI's `get_jieqi_name`, so the mapping can be checked.
- Entries are sorted by actual moment, strictly increasing. Within a Gregorian year the index order is 22, 23, 0,
  …, 21: Xiaohan (小寒) and Dahan (大寒) come first, and entries are not sorted by index.
- `year` is the owning year passed to the query. In the default window all 24 crossings of each year fall in the
  same Gregorian year, and the check verifies this. That does not always hold for high years: Xiaohan of 9999
  falls on 9998-12-31, so `year` differs from the year inside `iso_utc`.
- The default table keeps 2051 as a trailing year, so every moment in 1950–2050 still has its successor in the
  table.
- The time scale is **UT1**, not UTC+8 clock time; shown in UTC+8, the same moment may fall on a different date.
  The table's `timescale_note` describes the UT1 / UTC difference for each era. Do not infer the time scale from
  the `iso_utc` field name; read `timescale_note` before interpreting the timestamp fields.
  [Time scales](DESIGN.md#time-scales) explains how UT1 relates to UTC in this library.
- Sub-millisecond parts are truncated, not rounded; `iso_utc` and `unix_ms` denote the same millisecond. The
  output has no generation timestamp, so two runs at the same commit should produce identical bytes.

`./checks.py --jieqi-table` checks this contract, the HKO almanac baseline, and an independent recomputation by
`statistics/common.py`.
